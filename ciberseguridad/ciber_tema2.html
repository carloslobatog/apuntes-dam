Protocolo HTTP

El protocolo HTTP (Protocolo de Transferencia de Hipertexto) es la base de la comunicación en la World Wide Web. Funciona bajo un modelo cliente-servidor donde el navegador (cliente) hace una petición y el servidor web devuelve una respuesta.

  • HTTP (Puerto 80): Transmite toda la información en texto plano. Si un atacante intercepta la comunicación en cualquier punto de la red (un router comprometido, una red Wi-Fi pública), puede leer exactamente lo que el usuario está enviando o recibiendo. No hay confidencialidad ni integridad garantizada.
  • HTTPS (Puerto 443): Es la versión segura. Añade una capa criptográfica (SSL/TLS) entre HTTP y TCP. Antes de enviar cualquier dato, el cliente y el servidor negocian un túnel cifrado. Si alguien intercepta los paquetes, solo verá un bloque de datos incomprensible (Application Data) y no podrá leer contraseñas, cookies de sesión ni el contenido de la web.

Los Métodos HTTP principales

¿Cómo viajan los datos desde el navegador al servidor? Los dos métodos fundamentales son:

1. Método GET (Petición de recursos)

Se utiliza para solicitar información al servidor (ej. cargar una página web, una imagen).

  • El problema de seguridad: Si enviamos datos en un GET (por ejemplo, un formulario de login mal programado), estos viajan visibles en la propia URL:
    http://miservidor.com/login.php?usuario=admin&clave=12345
  • Incluso si usamos HTTPS, enviar credenciales por GET es una vulnerabilidad grave porque esa URL quedará registrada en el historial del navegador, en los logs del servidor web (ej.
    /var/log/nginx/access.log
    ) y en proxies intermedios.

2. Método POST (Envío de datos)

Se utiliza para enviar información sensible o extensa al servidor, como el envío de un formulario de inicio de sesión o la subida de un archivo.

  • La ventaja: Los datos no van en la URL, sino ocultos en el cuerpo (body) del mensaje HTTP.
  • El peligro real: Que no se vean en la URL de la pantalla no significa que estén cifrados. Si se usa POST sobre HTTP puro, el cuerpo del mensaje viaja en texto claro por la red de la clase.

En resumen, para proteger la información sensible, siempre se debe usar HTTPS y preferir el método POST para enviar datos confidenciales.

Introducción a Wireshark para la práctica

Wireshark es un analizador de protocolos de red que permite capturar y analizar el tráfico de red en tiempo real. A este tipo de programa se les llama sniffers.

Para esta demostración el objetivo es que actuemos como "atacantes" pasivos dentro de la propia red local (interfaz de red lo), capturando el tráfico mientras alguien se loguea en una web.

Preparación del escenario

Tener una web de prueba muy sencilla con un formulario de login configurado para usar el método POST. Estará disponible en HTTP (puerto 80) y HTTPS (puerto 443). Para ello, vamos a instalar el servicio NGINX, que nos permite levantar servidores de manera fácil e intuitiva. En las máquinas virtuales con Kali Linux (o cualquier distribución basada en Debian), la instalación es directa desde los repositorios oficiales: 


    sudo apt update 
    sudo apt install nginx 
    sudo systemctl start nginx 
    sudo systemctl enable nginx

Modificamos la configuración del servidor, para ello:

sudo nano /var/www/html/index.html

Y vamos a pegar este contenido:


    <!DOCTYPE html>
    <html>
    <head>
        <title>Laboratorio de Ciberseguridad</title>
    </head>
    <body>
        <h1>Prueba de intercepción HTTP</h1>
        <p>Esta página se ha cargado mediante una petición GET.</p>
        
        <!-- Formulario preparado para la siguiente práctica -->
        <h2>Acceso al sistema</h2>
        <form action="/login.php" method="POST">
            Usuario: <input type="text" name="usuario"><br>
            Clave: <input type="password" name="clave"><br>
            <input type="submit" value="Entrar">
        </form>
    </body>
    </html>

A continuación, modificamos los archivos de configuración de Nginx para cargar y actualizar el servidor. Para ello tenemos que acceder al directorio donde se guardan estos archivos:

cd /etc/nginx/sites-available/

Creamos un archivo de configuración:

sudo nano configuracion_practica_http

Y pegamos el siguiente contenido:


    server {
        listen 80;
        server_name localhost;

        root /var/www/html;
        index index.html;

        location / {
            try_files $uri $uri/ =404;
        }
    }

Ahora, tenemos que actualizar el enlace simbólico que indica qué archivo de configuración estará habilitado:

cd /etc/nginx/sites-enabled/ sudo ln -s /etc/nginx/sites-available/configuracion_practica_http .

Ahora recargamos el servidor para que coja la nueva configuración:

sudo systemctl reload nginx

Para confirmar que el servidor web está escuchando correctamente en el puerto 80 (HTTP), se puede comprobar con:

sudo netstat -tulnp | grep :80

La salida mostrará el proceso de Nginx escuchando en el puerto 80.

Capturando la petición GET

Con el servidor web funcionando, pasamos a Wireshark para analizar cómo el navegador solicita esa página al servidor.

  1. Iniciar la captura: Abre Wireshark y selecciona la interfaz de red que vayas a usar. Si el cliente y el servidor son la misma máquina virtual, selecciona la interfaz de bucle local (lo). Si están conectadas en red, selecciona la interfaz correspondiente (suele ser eth0).
  2. Aplicar el filtro: En la barra de búsqueda superior, introduce este filtro para descartar el ruido de fondo y presiona Enter: http.request.method == "GET"
  3. Generar el tráfico: Abre un navegador web y entra en la IP del servidor web (por ejemplo, http://localhost o [http://192.168.](http://192.168.)X.X).
  4. Inspeccionar el paquete HTTP: En Wireshark aparecerá una línea correspondiente a la petición. Al seleccionarla y desplegar la sección Hypertext Transfer Protocol en el panel inferior, los alumnos podrán observar campos clave:
    • Request Method: GET
    • Request URI: /index.html
    • Host: localhost
    • User-Agent: Información sobre el navegador y sistema operativo del cliente.

Si a continuación borras el filtro de la barra superior y buscas justo debajo el paquete de respuesta del servidor web (HTTP/1.1 200 OK), podrás seleccionar ese paquete, desplegar la sección Line-based text data y ver el código HTML exacto de la página web transmitido en texto completamente claro a través de la red.

Capturando la petición POST

Ahora vamos a capturar la petición POST que se genera al enviar el formulario de login.

El formulario que creamos en el archivo index.html ya está configurado con method="POST" y apunta a un archivo ficticio llamado /login.php. Aunque ese archivo PHP no exista en nuestro servidor Nginx (el navegador mostrará un error 404 "Not Found"), no importa: el navegador enviará los datos igualmente, y eso es exactamente lo que queremos capturar en la red.

1. Preparar la captura y el filtro:

En Wireshark, asegúrate de estar capturando en la interfaz correcta (lo si todo se hace en la misma máquina local, o eth0/enp0s3 si accedes desde otra máquina virtual). En la barra de filtros superior, introduce: http.request.method == "POST" Pulsa Enter. La pantalla debería quedarse en blanco, esperando el tráfico.

2. Enviar las credenciales:

Abre un navegador web y entra en la IP del servidor web (por ejemplo, http://localhost o http://192.168.X.X). Rellena el formulario de login con cualquier usuario y contraseña (por ejemplo, usuario: admin, clave: 123456) y pulsa "Entrar".

El navegador mostrará un error 404 porque login.php no existe, pero la petición ya ha viajado por la red.

3. Analizar la petición capturada:

Vuelve a Wireshark. Debería haber aparecido una única línea correspondiente a la petición HTTP POST. Haz clic sobre ella para seleccionarla. Fíjate que en la columna "Info", Wireshark ya te da una pista indicando que es un POST y que contiene datos tipo application/x-www-form-urlencoded.

4. Visualizar los datos del paquete y extraer la clave:

EN el panel central verás los detalles de la petición POST, incluyendo los datos enviados en el cuerpo de la solicitud:

  1. Frame / Ethernet / Internet Protocol / Transmission Control Protocol: Estas son las capas inferiores (físico, red, transporte). Aquí pueden ver las IPs y puertos de origen y destino.
  2. Hypertext Transfer Protocol: Al desplegar esta sección, verán las cabeceras HTTP. A diferencia del método GET, no verán las credenciales en el Request URI.
  3. HTML Form URL Encoded: application/x-www-form-urlencoded: Despliega esta última sección. Aquí aparecerán los campos exactos del formulario ("usuario"=admin y "clave"=123456).

Esta práctica demuestra empíricamente que utilizar el método POST no añade ninguna capa de seguridad criptográfica. Simplemente saca los parámetros de la URL y los mete en el cuerpo del mensaje, pero viajan en texto plano. Cualquiera con acceso a la red (un atacante haciendo un Man-in-the-Middle o alguien conectado a la misma red Wi-Fi abierta) puede robar la sesión.

Uso de HTTPS para cifrar la información

HTTPS (HTTP sobre SSL/TLS) proporciona una capa adicional de seguridad al cifrar la comunicación entre el cliente y el servidor. Esto impide que los atacantes intercepten y lean los datos transmitidos, incluso si tienen acceso a la red. Por lo que vamos a crear un certificado autofirmado (ideal para entornos de laboratorio) y a configurar Nginx para que escuche en el puerto 443 (HTTPS).

1. Generar un certificado SSL autofirmado

Recordemos que SSL es el protocolo de seguridad que se utiliza para cifrar la comunicación entre el cliente y el servidor. En la terminal de Kali (o Debian) ejecuta este comando de OpenSSL para generar una clave privada RSA de 2048 bits y un certificado válido por un año: 


    sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 
    -keyout /etc/ssl/private/nginx-selfsigned.key 
    -out /etc/ssl/certs/nginx-selfsigned.crt

El sistema hará varias preguntas sobre la información del certificado. Puedes dejar los valores por defecto o ingresar la información correspondiente.

2. Configurar Nginx para usar HTTPS

Una vez generado el certificado, necesitamos configurar Nginx para que utilice HTTPS. Abre el archivo de configuración de Nginx:


    sudo nano /etc/nginx/sites-available/default

Busca el bloque server { ... } y añade (o descomenta) las siguientes líneas para habilitar el puerto 443 y apuntar a los certificados que acabamos de crear: 


    server {
        listen 80 default_server;
        listen 443 ssl default_server; # Habilitar HTTPS
        
        ssl_certificate /etc/ssl/certs/nginx-selfsigned.crt;
        ssl_certificate_key /etc/ssl/private/nginx-selfsigned.key;

        root /var/www/html;
        index index.html index.htm index.nginx-debian.html;
        server_name _;
        
        # ... resto de la configuración ...
    }

Guarda los cambios y recarga Nginx para aplicar la nueva configuración:


    sudo systemctl reload nginx

3. Probar la conexión HTTPS y capturar el código en Wireshark

Abre un navegador web y entra en la dirección https://localhost o https://[tu-ip-local]. Es posible que el navegador muestre una advertencia de seguridad debido a que el certificado es autofirmado. Acepta la advertencia para continuar y verás la página web cargada de manera segura.

Ahora, si realizas la misma práctica de captura de tráfico con Wireshark, verás que los datos transmitidos están cifrados. Para capturar el tráfico HTTPS en Wireshark, sigue los mismos pasos que antes, pero esta vez asegúrate de filtrar por el puerto 443 o por el protocolo TLS. Verás que los paquetes capturados no muestran la información del formulario en texto claro, sino que están cifrados.

4. Enviar el formulario de manera segura

Rellena de nuevo el formulario con el usuario admin y la clave 123456, y dale a "Entrar". Si vamos a wireshark veremos lo siguiente:

  1. Ya no hay HTTP explícito: El filtro http.request.method == "POST" no devolverá ningún resultado. Para el "atacante" en la red, no hay ninguna petición web, solo tráfico TCP en el puerto 443.
  2. El Handshake SSL/TLS: Si miran los primeros paquetes de la conexión (tls.handshake), verán el Client Hello y el Server Hello intercambiando los algoritmos criptográficos. En el paquete Certificate, podrán ver en claro los datos falsos que introdujeron al ejecutar el comando openssl.
  3. Application Data: El paquete que realmente contiene el POST (el envío del formulario) aparecerá etiquetado en Wireshark como "Application Data".
  4. Imposible leer la clave: Al desplegar los detalles de ese paquete, la sección "HTML Form URL Encoded" ha desaparecido. En su lugar, solo verán la capa Transport Layer Security y un campo llamado Encrypted Application Data lleno de bytes aleatorios e ilegibles.

¿Se puede hackear actualmente HTTPS?

En la actualidad, HTTPS es considerado seguro y confiable para la mayoría de las aplicaciones web. Sin embargo, existen vulnerabilidades y ataques que pueden comprometer la seguridad si no se implementa correctamente:

Vulnerabilidades en versiones antiguas de SSL/TLS

Por defecto, Nginx y los navegadores actuales negocian TLS 1.3 o TLS 1.2 usando intercambio de claves efímeras (Diffie-Hellman, ECDHE). En este escenario, la clave privada RSA que hemos generado solo se usa para autenticar la identidad del servidor, no para cifrar los datos. Como la clave simétrica de sesión se genera al vuelo y se destruye al terminar, introducir la clave RSA en Wireshark no servirá de nada.

Es importante asegurarse de que el servidor web esté configurado para usar versiones modernas y seguras de TLS (como TLS 1.2 o TLS 1.3) y deshabilitar versiones obsoletas como SSL 2.0, SSL 3.0 y TLS 1.0.

El método SSLKEYLOGFILE

El método SSLKEYLOGFILE (sí, se llama así realmente) es el estándar actual en ciberseguridad para inspeccionar tráfico TLS moderno. En lugar de atacar el cifrado asimétrico (que PFS hace inútil), este método extrae las claves simétricas efímeras directamente de la memoria del navegador en el momento en que se generan, antes de que se destruyan. Es el mismo principio que utilizan los analistas de un SOC (Security Operations Center) para destripar malware de red, o la técnica que usa un troyano bancario instalado en el sistema operativo para robar datos antes de que la capa de red los cifre.

Vamos a explorar algunas de estas vulnerabilidades en detalle. Para ello, vamos a Wireshark -> Edit -> Preferences -> Protocols -> TLS (o SSL en versiones de Wireshark anteriores a la 3.0)

Busca el campo llamado (Pre)-Master-Secret log filename. Introduce la ruta absoluta de un archivo de texto donde se volcarán las claves. Por ejemplo: /home/usuario/ssl_keys.log

Verificación: A partir de este momento, Wireshark intentará leer ese archivo en tiempo real para aplicar cualquier clave de sesión que coincida con el tráfico capturado.

Abre una nueva terminal. Es vital exportar la variable de entorno y lanzar el navegador desde esa terminal. Escribe:


    export SSLKEYLOGFILE=/home/usuario/ssl_keys.log

Ahora lanza el navegador desde esa misma terminal. Por ejemplo, si estás usando Firefox, escribe:

    firefox

Ahora, cada vez que el navegador establezca una conexión TLS, volcará la clave de sesión en el archivo ssl_keys.log. Wireshark podrá leer este archivo y descifrar el tráfico HTTPS capturado.

La variable SSLKEYLOGFILE es local. Si ejecutas el comando export en la terminal, pero luego abres Firefox haciendo clic en su icono del menú de aplicaciones de Kali, el navegador se abrirá en un entorno diferente, no recibirá la variable y no guardará las claves de cifrado. Tiene que nacer de esa misma ventana. Para comprobar que lo has hecho bien, visita https://localhost en ese navegador que se acaba de abrir, vuelve a la terminal y ejecuta: 


    cat /home/usuario/ssl_keys.log

Si ves un bloque de texto que empieza por palabras como CLIENT_RANDOM, el navegador está volcando la memoria correctamente.

Esta técnica demuestra un concepto crucial en ciberseguridad: el cifrado de red no sirve de nada si el extremo (el endpoint) está comprometido. Para que un atacante pueda usar esta técnica exacta (o una variante), ya debe tener algún nivel de acceso o ejecución de código en la máquina de la víctima. No es un ataque que se pueda hacer "desde fuera" solo escuchando el Wi-Fi. Aquí tienes los casos reales donde este principio se aplica, tanto desde la perspectiva del atacante (Red Team/Cibercrimen) como del defensor (Blue Team):

  • 1. Post-Explotación (El atacante ya está dentro)

    • Si un atacante logra entrar en un equipo (por ejemplo, mediante un phishing con un PDF malicioso que le da una consola oculta o reverse shell), puede modificar silenciosamente el entorno del usuario. Podría inyectar la variable SSLKEYLOGFILE en el perfil del usuario (como en .bashrc en Linux o en las variables de entorno de Windows) y enviar ese archivo de texto periódicamente a su propio servidor. El beneficio para el atacante: Evita hacer ruido en la red. El firewall y el IDS/IPS de la empresa verán tráfico HTTPS legítimo saliendo del equipo, pero el atacante tendrá las claves para descifrarlo en su casa.

  • 2. Malware bancario (El atacante ya tiene un troyano en la máquina de la víctima)

    • El cibercrimen moderno no intenta romper la criptografía de TLS 1.3 interceptando el router, porque es matemáticamente inviable. En su lugar, usan malware (como el famoso Emotet o Trickbot) que se inyecta directamente en la memoria del navegador (Chrome, Firefox). En lugar de usar la variable de entorno, el malware hace API Hooking: intercepta las funciones internas del navegador que manejan el texto en claro justo antes de que el navegador aplique el cifrado SSL/TLS. Para el usuario, el candado verde está puesto, pero el malware ya ha robado la contraseña.

  • 3. SOC (El analista de seguridad ya tiene acceso a la memoria de los endpoints para inspeccionar tráfico cifrado)

    • Este es el caso de uso profesional más habitual para esta técnica exacta. Cuando un analista de un SOC (Centro de Operaciones de Seguridad) captura un malware nuevo, lo encierra en una máquina virtual aislada (Sandbox) para ver qué hace. El malware moderno se comunica con sus creadores (servidores C2) usando HTTPS para ocultar las órdenes que recibe. El analista fuerza a la máquina virtual a volcar las claves de memoria para poder descifrar el tráfico en Wireshark y descubrir qué está intentando robar el virus o a qué IPs se está conectando.

  • 4. Inspección Corporativa (DLP y Antivirus)

    • En muchas empresas, los administradores de sistemas instalan agentes en los ordenadores de los empleados. Estos agentes utilizan técnicas similares para extraer las claves simétricas o instalan certificados raíz corporativos. El objetivo es que el firewall de la empresa pueda abrir y leer el tráfico HTTPS de los empleados en tiempo real para evitar la fuga de datos (DLP - Data Loss Prevention) o bloquear la descarga de virus ocultos dentro de conexiones seguras.
